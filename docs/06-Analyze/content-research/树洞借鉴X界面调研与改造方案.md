# 树洞借鉴 X 界面：调研与改造方案

> 类型：设计调研与实施方案 · 调研：2026-10-12 · 方案：2026-10-13（Asia/Singapore）· 状态：待评审。本文提出方案，不代表已批准或已修改界面。

**建议**：Web 与 Expo App 的树洞统一采用 X 式“单列连续帖子流 → 帖子详情与回复串 → 正文优先发布”的阅读路径。Web 沿用站点现有三栏外壳，把中栏的两列瀑布流改成一列；App 保留已批准的“广场”顶部模块 Tab 和底部五格导航，只改树洞子视图。首轮复用现有帖子、标签、点赞、评论和图片 API；预计需要改动 Web、App 两套视图及其共用的 API 消费层，具体工期须在视觉稿和验收范围确定后估算。最大风险是“全面采用”被理解成复制 X 的关注流、转发与书签；这些能力目前没有树洞后端数据。请先确认本文所述的**界面与交互借鉴范围**，再开始视觉原型和开发。

**范围**：树洞的列表、搜索、详情、回复与发布，以及与它直接相连的导航状态。万能墙保持独立匿名流；食堂、社团、热搜等其他内容流不随本轮统一换肤。下述尺寸是 **Dorm 拟定规格**，不是 X 当前客户端的实测值。

## 一、证据能支持到什么程度？

- 调研对象是 X 的信息流交互模式，不是可直接复用的 React/React Native 组件库。下文的“帖子卡片”“编辑器”“导航”等是设计构件名称，不表示 X 对外提供了相应组件源码。
- 一手资料为 [X Help Center](https://help.x.com/en/using-x)、[X 品牌指南 PDF](https://about.x.com/content/dam/about-twitter/x/brand-toolkit/x-brand-guidelines.pdf) 及 [X 商标政策](https://help.x.com/en/rules-and-policies/x-trademark-policy)。帮助页描述功能与操作，但不是完整设计规范；不能从中推出当前客户端的精确间距、字号、断点、图标尺寸或所有账号都可见的实验功能。
- 通过 agent-reach 检查：X 的 `twitter-cli` 已安装，但登录态后端未实时验证；本次未访问用户个人时间线，也未以登录态逐屏测量 X 客户端。Exa 免费搜索返回空结果及 429；后续用 agent-reach 的 Jina 网页阅读和官方域名检索继续核实。部分帮助页经 Jina 读取时返回 403，但官方检索索引仍可读取摘要；凡取自摘要的事实，本文只写摘要直接支持的部分。

## 二、X 官方资料能确认哪些模式？

### 2.1 信息流与帖子入口

X 的首页至少区分 **For you** 与 **Following** 两种时间线；前者含关注账号与主题的内容及推荐，后者只显示关注账号的帖子。两者可通过顶部标签点击或滑动切换，关闭后会保留最后打开的时间线。帖子正文区域可点入详情，详情承载图片、视频与关联信息。时间线中也可能出现转发和推广内容。[来源：For you 时间线](https://help.x.com/en/using-x/x-timeline)

**设计推断：** 树洞可借鉴“顶部少量切换项 + 单列连续信息流 + 点入详情”的组织方式；是否要做算法推荐、关注时间线或推广位，属于项目产品决策，不能由 X 的布局推出。

### 2.2 帖子构件与操作

X 的帖子可含文本、链接、照片、GIF 和视频。官方说明中，普通发帖上限为 280 字符，最多 4 个媒体项；更长帖子属于 X Premium 能力。这些是 X 的产品规则，不应照搬为树洞的数据限制。[来源：How to Post](https://help.x.com/en/using-x/how-to-post)

X 的回复从帖子的回复图标进入；用户在时间线点击回复可展开其所回复的原帖。转发会带有转发者提示；“引用帖子”将原帖作为被引用对象，同时允许添加自己的评论或媒体。[来源：回复和提及](https://help.x.com/en/using-x/mentions-and-replies)、[来源：Repost FAQs](https://help.x.com/en/using-x/repost-faqs)、[来源：How to Repost](https://help.x.com/en/using-x/how-to-repost)

书签用于个人稍后阅读；X 帮助中心说明书签仅本人可见，可从导航菜单的 Bookmarks 入口访问。[来源：About Bookmarks](https://help.x.com/en/using-x/bookmarks)

**设计推断：** 一张树洞帖子应把“作者与时间、正文、媒体、上下文提示、回复/互动、更多操作”做成稳定的视觉层级，并让保存、举报等低频操作保持可达。是否启用转发、引用、公开互动计数与书签，需按树洞社区边界逐项决定。

### 2.3 编辑器与讨论串

X 的编辑入口支持多媒体内容；普通发帖展示字符进度。会话控制可在发帖时选择谁可以回复，也可在发出后调整，默认选项为所有人可回复。[来源：How to Post](https://help.x.com/en/using-x/how-to-post)、[来源：About conversations](https://help.x.com/en/using-x/x-conversations)

X 的 thread 是同一作者连续发布的一串帖子。官方帮助页描述在编辑器里以加号追加帖子、超限高亮、统一“Post all”；时间线中的短串可用连线呈现，较长串折叠为“Show this thread”，进入后阅读完整上下文。[来源：How to create a thread](https://help.x.com/en/using-x/create-a-thread)

**设计推断：** 树洞可以先借鉴编辑器“正文先行、媒体附件、发布动作固定可见、回复范围清晰”的结构，以及详情页的“原帖—回复”上下文；是否引入连续发帖的 thread 编辑能力取决于需求，不是形成 X 式界面的前提。

### 2.4 搜索、筛选与导航

X 搜索可查帖子、账号和话题，并在结果页用顶部类别标签切换；官方页面列出 Top、Latest、People、Photos、Videos 等分类，以及可见内容筛选。高级搜索在登录后的网页端提供词、人物、地点和日期等条件。不同官方帮助页列出的类别并不完全一致，说明不能把某一个标签集合当成固定跨平台规范。[来源：How to use X search](https://help.x.com/en/using-x/x-search)、[来源：Search result FAQs](https://help.x.com/en/using-x/top-search-results-faqs)、[来源：Advanced search](https://help.x.com/en/using-x/x-advanced-search)

X 官方帮助页明确提到搜索在移动端从 Explore 标签进入，通知由 Notifications 标签承载，书签位于导航菜单；桌面网页还提供 `n` 新建帖子、`r` 回复、`/` 搜索、`j/k` 切换帖子、`?` 查看快捷键等键盘操作。[来源：How to use X search](https://help.x.com/en/using-x/x-search)、[来源：回复和提及](https://help.x.com/en/using-x/mentions-and-replies)、[来源：About Bookmarks](https://help.x.com/en/using-x/bookmarks)、[来源：How to Post](https://help.x.com/en/using-x/how-to-post)

**设计推断：** 可借鉴“搜索入口明确、结果分类少而稳定、移动导航和桌面快捷操作分层”的思路；树洞搜索分类应依据本项目现有内容类型，不直接照搬 X 的 People/Media/Lists 等类别。

### 2.5 无障碍和内容安全

X 提供图片替代文本，发帖时可通过图片上的 `+ALT` 添加。其帮助页说明替代文本使盲人、低视力及辅助技术用户能理解图片；官方也列有键盘快捷键。X 还提供隐藏回复及查看被隐藏回复的入口。[来源：How to add image descriptions](https://help.x.com/en/using-x/add-image-descriptions)、[来源：Accessibility features](https://help.x.com/en/using-x/accessibility-features)、[来源：回复和提及](https://help.x.com/en/using-x/mentions-and-replies)

**设计推断：** 若树洞以 X 式密集信息流为方向，仍需保留可读的触控目标、屏幕阅读器标签、图片描述、焦点顺序和清晰的举报/隐藏反馈；视觉相似不能代替无障碍验证。

## 三、品牌和复用有什么边界？

X 官方品牌指南覆盖标志、品牌色、字体和术语等资产使用；商标政策指出，会误导用户以为与 X 有关联的商标使用可能违规。官方品牌工具页目前仍包含部分 Twitter 旧资产，与 X 品牌指南并存，不能把旧页面中的下载素材当作树洞界面素材包。[来源：X 品牌指南](https://about.x.com/content/dam/about-twitter/x/brand-toolkit/x-brand-guidelines.pdf)、[来源：品牌工具页](https://about.x.com/en/who-we-are/brand-toolkit)、[来源：商标政策](https://help.x.com/en/rules-and-policies/x-trademark-policy)

**设计推断：** 借鉴信息架构、密度和交互节奏时，应使用 Dorm 自有名称、标志、配色和图标；不要让界面表现出 X 官方客户端或联名产品的身份。这是设计风险控制建议，不是对整体 UI 模仿是否合法的法律结论。

## 四、哪些细节尚未核验？

- 当前 X iOS、Android 和网页端的像素级布局、断点、图标形状、字体度量与实时 A/B 实验；需要逐屏截图和尺寸测量才能作为视觉稿依据。
- 具体浏览权限、功能灰度和付费差异。帮助页可能持续更新，实施前应重新打开对应页面和目标设备核对。
- X 没有在上述帮助页公开可直接安装的“Twitter UI 组件库”；若项目说“采用 Twitter 组件”，目前只能确定为借鉴交互构件，不能据此承诺复用官方代码。

## 六、建议采用什么界面？

**结构选择：借鉴 X 的阅读路径，使用 Dorm 的身份和导航。** Web 原有三栏外壳已经包含左侧站点导航和右侧辅助栏；树洞路由把中栏变为一条连续帖子流，并把当前占高 120px 的图片页头收成紧凑的站点顶栏。Expo App 的底部导航和广场顶部模块 Tab 保留，树洞内容占屏幕宽度。这样两端在“读一张帖、进入讨论、返回原位置”上统一，而平台导航仍符合现有产品决定。Web 页头只在树洞相关路由调整，不连带修改其他站点页面。

```text
Web 宽屏：站点导航 | 树洞标题／标签筛选／单列帖子流 | 搜索／热门标签／校园推荐
Web 窄屏：树洞标题 → 标签筛选 → 单列帖子流；沿用现有底栏
Expo App：广场顶部模块 Tab → 树洞单列帖子流；沿用现有底栏与发布中心
```

| 构件 | 拟定行为与视觉层级 | 复用和边界 |
| --- | --- | --- |
| 信息流头部 | 标题“树洞”；其下为可横滑的现有标签筛选。列表按时间排列，显示“最新”，不把它叫“为你推荐”。搜索作为清晰入口。没有第二种真实排序前，不画一个只有一项的时间线 Tab。 | Web 复用 `TreeHoleToolbar`；App 复用 `TopTabStrip` 的模块导航，标签采用筛选控件而非再造一级导航。 |
| 帖子行 | 作者头像/昵称、发布时间在首行；标题作为加重的第一行，完整正文在其后；1–3 张图在正文后；底部一排“回复、赞、更多”。行与行用细分割线，不用瀑布流错位、玻璃遮罩、大阴影。公告只在有权限的场景显示明确标记。 | Web 从 `PostCard` 收敛首页、搜索、标签和个人帖子；App 在现有帖子域组件/列表原型内实现。标题仍必填，后续若要变为 X 式无标题发帖需另改服务端规则。 |
| 帖子详情 | 原帖完整呈现，图片可打开；回复按现有一级/二级关系依次显示。回复输入保持可见；长内容不在卡片中截断。删除、举报放到有权限的“更多”菜单。返回恢复列表位置。 | Web 沿用 `PostDetailShell` 并逐一检查树洞、校园此刻、热搜调用方；App 沿用 `DetailScreen` 与现有互动逻辑。 |
| 发布器 | 正文是视觉主区；标题、标签、图片控件清晰但次要；发布按钮在可见位置，提交失败保留输入。 | Web 沿用 `PostNew`，App 沿用中央发布中心和已注册的树洞表单。现有三图限制、双语文案与服务端校验保持一致。 |
| 右侧辅助栏 | 宽屏只放现有搜索入口、热门标签和真实校园推荐数据；窄屏下沉或隐藏，不重复帖子操作。 | 复用 `SiteWebShell` 的右栏与 `useShellAside`；不新增“推荐关注的人”占位块。 |

**视觉方向（Dorm 拟定，待原型确认）**：内容背景用现有语义表面色，正文用系统/现有 UI 字体，作者和正文优先，时间/标签退后。App 强调色继续取厦大蓝令牌，发布等既有动作仍按 App 令牌；Web 取本站的品牌语义令牌。最醒目的改动是“正文直接成为信息流主体”，不是换一个 X 标志、黑底或一套新图标。所有视觉值从已有令牌取，不在页面里散落新色值。需要深色模式时，应按两端现有主题系统设计与验收。

原型尺寸建议：Web 中栏阅读宽度约 **600–680 CSS px**，帖子正文 **15–16 CSS px**，横向内边距 **12–16 CSS px**；以上是待真机与宽屏截图校准的起点，不是 X 官方数值。Web 按 WCAG 2.2 检查对比度和键盘焦点。App 触控目标沿用项目宪法的 **iOS ≥44×44 pt / Android ≥48×48 dp**，字号与间距只取现有令牌，并实测中文/英文换行和系统字号放大。

## 七、按什么顺序实施并验收？

| 阶段 | 实施范围 | 当阶段验收 | 回退办法 |
| --- | --- | --- | --- |
| 0. 视觉原型 | 做 Web 宽屏/窄屏与 Expo App 的同一帖子样例，并覆盖纯文字、三图、长文、公告、两级回复、加载和错误态。先确认信息密度及“全面采用”的外观边界。 | 用真实双语内容评审；验证正文、图片、操作与现有导航均清楚可见。 | 只撤回原型，无生产改动。 |
| 1. Web 信息流 | 让树洞首页与搜索/标签页消费同一帖子行；改首页两列为单列，保留分页、预取、滚动恢复和推荐右栏。 | 列表顺序、标签/搜索、点赞、进详情再返回、窄屏滚动与图片加载通过；桌面和手机截图核对。 | 以独立变更提交；若验证失败，回退该提交恢复原列表视图。 |
| 2. Web 详情与发布 | 收紧 `PostDetailShell` 的阅读/回复结构，重排 `PostNew`。检查它的其他调用方。 | 原帖、二级回复、登录拦截、删除/举报权限、图片预览、发布失败输入保持；相关后端测试与 Web 构建通过。 | 回退本阶段视图提交；后端数据与接口保持原状。 |
| 3. Expo App 树洞 | 在广场现有树洞 Tab 内实现同样的帖子信息层级；复用列表、帖子域组件、详情和发布中心。 | Expo Go 上 Android/iOS 真机或模拟器检查触控、系统字体放大、读屏、深链与滚动位置；类型检查及相关测试通过。 | 回退 App 视图提交，保留原 `CampusFeed`。 |

建议每阶段只替换**一个消费点的表示层**，不先重写帖子 API。Web `PostCard` 和 `PostDetailShell` 有多个调用方，变更前须逐一核对。App 设计宪法要求先声明页面原型、消费令牌和公共组件，并禁止为树洞单独复制一套通用卡片；该约束在第 3 阶段作为验收门槛。

## 八、哪些事现在需要决定？

1. **“全面”是否包含新的社交数据功能？** 当前推荐范围是 UI、布局和现有互动。若要“关注中”、转发/引用、书签、浏览量或“谁能回复”，先为每一项写明权限、数据模型、接口和通知规则，再单独排期。解决方式：评审原型时逐项勾选需要的能力，不用不可点击的假图标代替。
2. **普通树洞帖是否继续强制标题？** 当前服务端拒绝无标题普通帖。推荐首轮保留标题并让它成为正文前的加重首行，以免把视觉改造升级成数据迁移。若产品要完全按 X 的无标题短帖方式发布，再决定旧帖展示与新帖校验如何兼容。
3. **优先交付哪一端？** 上表按 Web → App 排序，因为 Web 首页差异最大且共享的 `PostCard` 可同时统一搜索/标签页。若下一期重点是 Expo Go 演示，可交换第 1 与第 3 阶段；两端使用同一份原型与验收样例。

**不在本方案范围**：复制 X 的商标、logo、图标文件、字体或官方客户端的像素值；把万能墙并入树洞；让其他广场模块跟着树洞换肤；增加广告、算法推荐、关注图谱、转发、书签或浏览统计。它们各自需要明确的产品和服务端需求。本文也不作商标法律判断。
